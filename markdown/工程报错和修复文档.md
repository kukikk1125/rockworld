## 3. 报错 1：`spawn EPERM`

### 3.1 现象

`next-dev.err.log` 中出现：

```text
Error: spawn EPERM
errno: -4048
code: 'EPERM'
syscall: 'spawn'
```

### 3.2 根因

这是开发环境启动子进程时的权限型错误，通常与以下情况相关：

- 旧进程占用
- Windows 权限限制
- 启动方式与当前终端环境冲突

### 3.3 修复建议

- 先确认旧的 `next dev` 进程是否仍在运行
- 换新端口重新拉起 dev 服务
- 若当前终端启动异常，使用新的 PowerShell 窗口重新启动
- 不要默认相信旧端口展示的是最新页面

### 3.4 当前影响判断

这类问题主要影响开发验证，不直接说明业务代码有逻辑错误，但会严重干扰“看到的页面是不是最新代码”的判断。

## 4. 报错 2：`next start` 与 `output: "export"` 冲突

### 4.1 现象

`next-start.err.log` 中出现：

```text
"next start" does not work with "output: export" configuration.
Use "npx serve@latest out" instead.
```

### 4.2 根因

`next.config.ts` 当前在生产环境中启用了：

- `output: "export"`

这意味着项目生产构建产物是纯静态导出目录，不适用于 `next start` 方式预览。

### 4.3 正确修复方式

- 日常交互验证：使用 `npm run dev`
- 导出产物预览：使用静态服务器去服务 `out` 目录
- 不再把 `next start` 当作这个项目的生产预览手段

### 4.4 当前结论

这不是“代码坏了”，而是“启动方式错了”。

## 5. 报错 3：`.next` 构建缓存损坏

### 5.1 典型现象

历史上已出现过类似错误：

- `Cannot find module './548.js'`
- `._next/static/...` 缺少 chunk
- 页面黑屏或资源加载异常

### 5.2 根因

- `.next` 目录中的构建缓存残缺
- 旧缓存与新代码不匹配

### 5.3 修复方式

- 删除 `.next`
- 重新执行 `npm run build`
- 重新核验页面

### 5.4 预防建议

- 一旦出现“明显不是最新代码”的情况，不要一直在旧缓存上排查业务逻辑
- 优先排除构建产物污染

## 6. 报错 4：GitHub Pages 子路由 404

### 6.1 现象

首页可访问，但进入以下子页面时可能出现 404：

- `/history`
- `/pets`
- `/settings`

### 6.2 根因

静态导出时，如果只生成平铺 `history.html` 之类文件，而部署环境更适合目录式路由，就会导致 GitHub Pages 子路径访问失败。

### 6.3 当前修复方案

在生产配置中启用：

- `trailingSlash: true`

这样导出结构更偏向：

```text
out
├─ history
│  └─ index.html
├─ pets
│  └─ index.html
└─ settings
   └─ index.html
```

### 6.4 验证重点

部署前必须确认：

- `out/history/index.html`
- `out/pets/index.html`
- `out/settings/index.html`

确实存在。

## 7. 报错 5：动态详情页线上 404

### 7.1 现象

以下形式的 URL 在线上静态站点中无法正常命中：

- `/rockworld/tasks/{id}`
- `/rockworld/spirits/{id}`

### 7.2 根因

- 任务 `id` 和精灵 `id` 依赖运行时本地数据
- GitHub Pages 只能服务构建时已经存在的静态文件
- 运行时生成的动态 `id` 不会提前出现在 `out` 中

### 7.3 当前修复方案

统一改用静态页 + 查询参数：

- `/rockworld/tasks/view/?taskId=...`
- `/rockworld/spirits/view/?spiritId=...`

### 7.4 代码层面的现状

当前首页、记录页、图鉴页、精灵详情页都已经按照这个思路跳转：

- `router.push("/tasks/view?taskId=...")`
- `href="/spirits/view?spiritId=..."`

### 7.5 结论

这是当前部署模式下必须长期保留的约束，不建议再回到运行时动态详情路径作为线上主入口。

## 8. 报错 6：嵌套布局误写 `<html>` / `<body>`

### 8.1 现象

历史问题表现为：

- 页面结构异常
- 局部路由渲染不稳定
- 页面黑屏或样式异常

### 8.2 根因

在 Next.js App Router 中，只有根布局可以输出完整文档结构。

### 8.3 正确做法

- 只有 `src/app/layout.tsx` 输出 `<html>` 和 `<body>`
- 其他页面和子布局只输出片段或普通容器

### 8.4 当前状态

当前根布局 `src/app/layout.tsx` 已按正确方式处理。

---

## 9. 报错 7：嵌套 button 导致交互异常

### 9.1 现象

历史上出现过：

- 整卡可点但内部删除按钮失效
- 点击行为串扰
- 浏览器交互不稳定

### 9.2 根因

可点击卡片如果本身是 `<button>`，内部再嵌套真实 `<button>` 会造成无效 HTML 结构和交互问题。

### 9.3 当前修复方式

现有实现已改为：

- 外层使用 `div role="button"` 承载整卡点击
- 内层真实操作按钮继续使用 `<button>`
- 内层按钮点击时 `stopPropagation()`

### 9.4 当前受影响位置

- 首页进行中任务卡
- 记录页任务卡

---

## 10. 报错 8：中文编码污染 / 文档乱码

### 10.1 现象

当前 `markdown` 目录中的部分旧文档已经出现乱码，例如：

- 中文正文显示为异常字符
- 终端查看与浏览器展示不一致

### 10.2 根因

常见原因包括：

- 文件编码被错误保存
- 终端编码页与文件编码不一致
- 通过不稳定工具链重写中文文档

### 10.3 当前修复策略

- 新文档统一按 UTF-8 保存
- 不直接复用已有乱码内容
- 以当前源码中的真实文案和逻辑重新整理文档

### 10.4 后续建议

- 文本密集文件尽量避免经过会二次转码的流程
- 文档校对时不要只看终端输出，也要检查编辑器实际显示

## 11. 删除任务与异色存档的数据语义说明

这不是报错，但属于非常容易误判的“数据行为问题”。

### 当前真实行为

- 删除任务：只删除任务过程
- 已存档异色：保留

### 对应代码与文案

首页和记录页确认弹窗都明确说明：

- `该操作只删除任务过程，不删除已经存档的异色成果。`

### 风险

如果后续有人误以为删除任务会清空存档，可能会把这当作 bug。

因此建议在后续迭代中继续保持该语义一致，不要文案和实现分离。

---

## 12. 推荐验证流程

每次较大更新后，建议至少做这组验证：

1. 检查是否还有旧 dev 进程和旧端口页面残留。
2. 如页面异常，优先排除 `.next` 缓存问题。
3. 使用 `npm run dev` 做交互验证，不用 `next start` 预览静态导出项目。
4. 核对一级路由是否可正常打开：
   - `/`
   - `/history`
   - `/pets`
   - `/settings`
5. 核对详情页跳转是否仍使用查询参数形式：
   - `/tasks/view?taskId=...`
   - `/spirits/view?spiritId=...`
6. 导出部署前检查 `out` 目录是否为目录式子路由结构。
7. 文案更新后检查中文是否出现乱码。

---

## 13. 当前结论

当前最关键、最真实的工程风险集中在四类：

- 启动方式与部署方式不匹配
- 静态导出与动态路由模型冲突
- 本地缓存或旧进程干扰验证
- 中文文档编码污染

本轮新增的四份文档已经按这些风险重新整理，后续如果再更新页面或路由，建议同步更新本文件，作为工程交付时的“故障记忆库”。
